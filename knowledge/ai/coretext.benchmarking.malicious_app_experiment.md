## Highlights
**How to Read and Apply the Benchmarking Papers to Your Web App Experiment**

Do not read these papers for their syntax or specific tasks (they don't test React). Read them to understand the **psychology of the test**—how they apply structural pressure to force LLMs into failure modes.

1. **SlopCodeBench (arxiv:2603.24755) - Focus on "The Pivot" and "Slop" Metrics**
   - **What to read:** Section 2 (Design Principles) and Section 4.1 (Iterative Agent Trajectories Accumulate Quality Issues). Look closely at the `code_search` example on page 3.
   - **The Lesson:** The benchmark allows the agent to build a naive, hardcoded structure early on, then introduces a requirement that violates those early assumptions, forcing a massive refactor. LLMs hate refactoring and will instead bolt new logic onto old code, creating "slop".
   - **How to apply it:** This is the logic behind Checkpoints 3 and 5 in your plan. You let the agent build a simple Grid View (Checkpoint 1). Then, later, you demand a Map View that must share the exact same complex filter state (Checkpoint 5). If they didn't architect their state management cleanly early on, they will be forced to duplicate massive amounts of code.
   - **Measurement:** Pay attention to Section 2.3 (Measuring Code Quality). You must figure out how to run Cyclomatic Complexity checks (like ESLint complexity rules) and AST-Grep across your React codebase at *every single checkpoint* to mathematically prove that Superpowers created "God Components" and Coretext v2 did not.

2. **ProjDevBench (arxiv:2602.01655) - Focus on "Constraint Amnesia"**
   - **What to read:** Section 5.1 (Where End-to-End Coding Agents Fail) and Section 5.2 (Insights from Code Review). 
   - **The Lesson:** Agents often achieve functional correctness (the code works) but fail the Code Review because they violate strict, explicit rules (e.g., using forbidden libraries or modifying protected files). Their attention gets entirely consumed by the complex business logic of the new feature, causing them to forget global architectural constraints.
   - **How to apply it:** This is the logic behind your Global Architectural Constraint: *"All state MUST be managed via URL query parameters. Local `useState` is strictly forbidden for filtering."* By Checkpoint 3 or 4, when the filtering logic gets extremely complex (arrays of checkboxes, localStorage hydration), prompt-heavy frameworks like Superpowers will suffer Constraint Amnesia. They will quietly slip `useState` into the component because it's easier, failing the architectural test. Coretext v2's Reviewer, reading the immutable `ARCHITECTURE.md`, should catch and block this.

3. **EvoClaw (arxiv:2603.13428) - Focus on "Recall vs. Precision" and "Snowball Effect"**
   - **What to read:** Section 1 (Intro) and Section 5.4 (Recall Scales while Precision Saturates).
   - **The Lesson:** While LLMs can keep adding new features (Recall), they are incapable of preventing regressions (Precision) as the system evolves. Unresolved regressions trigger a "snowball effect" of accumulating technical debt.
   - **How to apply it:** Use EvoClaw's "Develop-in-place, evaluate-in-isolation" methodology. Define F2P (Fail-to-Pass) tests for Recall and P2P (Pass-to-Pass) tests for Precision. Coretext v2's Reviewer is mechanically required to solve the "Precision" problem that LLMs cannot solve via prompts alone.

4. **SWE-CI (arxiv:2603.03823) - Focus on "EvoScore"**
   - **What to read:** Section 2.3 (EvoScore).
   - **The Lesson:** It provides a mathematical formula for measuring code quality over time, weighting later iterations more heavily to penalize technical debt accumulation.
   - **How to apply it:** Calculate an EvoScore for the final 5-iteration trajectory, proving that Coretext v2 maintained a higher trajectory of functional correctness.

5. **Interaction Smells (arxiv:2603.09701v2) - Focus on "Must-Do Omission" and "Must-Not Violate"**
   - **What to read:** Figure 1 (Taxonomy of Interaction Smells) and Section 4.2.2 (Must-Do Omission).
   - **The Lesson:** Proves that "Constraint Amnesia" is a documented scientific phenomenon.
   - **How to apply it:** Use this taxonomy as a qualitative penalty ledger. Track "Must-Not Violate" events when Superpowers forgets the global URL constraint and uses `useState`.

## Problems & Solutions
- **Problem**: The advisor demands a visual, working web app, but rigorous scientific benchmarks (ProjDevBench, SlopCodeBench) evaluate headless CLIs and APIs. Building a simple web app proves nothing about Coretext v2's ability to prevent long-term structural degradation.
  - **Solution**: Design a "Malicious Web App Test" (`experiments/trore-web-eval/checkpoints.md`). This experiment uses 5 iterative checkpoints that start simple (to appease the advisor with a working MVP) but introduce hostile, cascading requirements and strict global constraints (e.g., URL-driven state only). This forces prompt-heavy frameworks into measurable structural erosion (God Components, Constraint Amnesia), proving the necessity of Coretext v2's mechanical Reviewer.
- **Problem**: Reusing old BMad artifacts (`architecture.md`, `epics.md`) for the new experiment provides the agents with a pre-defined architecture.
  - **Solution**: Abandon the rigid artifacts. The experiment must start from a natural language prompt (greenfield) so the agent is forced to make early architectural decisions. If you spoon-feed them the architecture, they can't make bad design choices, and you cannot measure structural erosion over time.
- **Problem**: Unconstrained prompt frameworks (like Superpowers) finish tasks quickly but degrade over time, while minimal prompt philosophies (like Coretext v2) might be too bare-bones to write complex boilerplate effectively.
  - **Solution**: Reframe the experiment to treat Superpowers as the "User-Space Executor" and Coretext v2 as the "Operating System / Kernel". Run Superpowers alone (Control) vs. Superpowers governed by Coretext v2's Planner and Reviewer (Treatment), ensuring cold-booted, isolated sessions that wipe context window exhaustion.
