# A Platform to unite every diferent workflows

Việc tạo ra 1 khung hoàn hảo là bất khả thi. trong khi thị trường đã có quá nhiều các workflow, các component rất tốt. giờ cần tạo 1 nền tảng cho phép ghép bất cứ workflow nào vào. Thống nhất qua 1 file JSON làm interface, kết nối upsert thẳng vào SurrealDB, đồng thời làm interface agent có thể đọc và sửa trực tiếp
- **Lõi Coretext (Python Daemon) sẽ đọc file JSON.** Nó đóng vai trò là Orchestrator (Người điều phối).
- File JSON này chỉ chứa **siêu dữ liệu (metadata)** mô tả thứ tự gọi các lệnh CLI hoặc đọc các file của các methodology có sẵn.
- **Ví dụ luồng lai (Hybrid Flow) mô tả bằng JSON:** Bạn có thể định nghĩa một quy trình: _Thiết kế bằng [[resource/spec-kit]] -> Code bằng [[resource/Conductor Extension]] -> Quản lý dự án bằng [[Beads]] -> Test bằng [[BMAD Test Architect]]_.
- **Data Nodes (Node Dự án):** Chứa dữ liệu thực tế. BMad sinh ra file `architecture.md` hay Spec Kit sinh ra `spec.md`, Coretext sẽ parse các file này thành Data Nodes.
- **Process Nodes (Node Quy trình/Instruction):** Chính là các bước (`steps`) được parse từ file JSON ở trên.
	- Có thể chứa các instruction hoàn chỉnh của các method trên
	- có thể là các agent skill
	- có thể là các bước manual của con người
	- có thể là hành động git commit/push/PR/...
- **Cấu trúc Schema đề xuất:** Bất kỳ Node nào do Agent tạo ra trong file JSON DAG cũng phải tuân thủ ontology cơ bản của đồ thị:
    - `id`: Khóa chính (Canonical ID).
    - `type`: Loại bước (ví dụ: `PlanningNode`, `ExecutionNode`, `ReviewNode`).
    - `status`: Trạng thái (`pending`, `in_progress`, `done`, `failed`).
    - `dependencies`: Mảng chứa ID của các bước trước đó. (Lớp logic của Coretext sẽ tự động dịch mảng này thành các cạnh `DEPENDS_ON` trong SurrealDB).
    - `context_query`: Chuỗi truy vấn (để dùng GraphRAG gọi đúng context cần thiết).
- Visualize bằng JSON Crack hoặc React Flow
