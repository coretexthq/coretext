## Summary
Discussed the shift from heavy spec-driven development (like BMAD and Superpowers) to a leaner, State-Driven Development approach for Coretext. The optimal architecture uses a 2-agent adversarial loop (Planner/Reviewer Agent A and Executor Agent B). Knowledge files are divided into "Intent" (a single `ARCHITECTURE.md` acting as a pointer, `docs/`, and agent skills) and "Execution" (ephemeral planning artifacts translated into semantic intent). These session artifacts avoid Agile "slop" and are logged in `experience.json`, ingested into the SurrealDB graph, and serve as "Background Intuition" for future sessions.

## Problems & Solutions
- **Problem**: Spec-driven methodologies ([[BMAD]], [[Superpowers]]) generate "Agile slop" (massive PRDs, sprint proposals, rigid user stories) that poison the AI's context window and cause architectural drift when reality changes during implementation.
  - **Solution**: Adopt State-Driven Development where `ARCHITECTURE.md`, `docs/`, and `skills/` define the constraints (Intent). When mid-implementation drift occurs, execution stops immediately to update the State (Markdown files) before resuming coding. Small bug fixes are handled directly during execution.
- **Problem**: Forcing an agent to write tests and code in separate sessions causes context loss, while writing static execution checklists creates "Topology Blindness" and pollutes the knowledge graph with temporal data.
  - **Solution**: Implement a 2-agent adversarial loop. Agent A (Planner/Reviewer) writes a strict, ephemeral Sprint Contract. Agent B (Executor) handles the TDD micro-loop (writing the failing test and implementation). Agent A returns to audit the work and translates the ephemeral execution checklist into a permanent "Episodic Anchor" (semantic learning) that gets appended to `experience.json` for SurrealDB ingestion.
- **Problem**: Long-running agents face "context window degradation" and "context anxiety" across massive sprints.
  - **Solution**: Enforce stateless, "Single Issue per Session" execution. A session targets one cohesive issue, keeping the context pristine and eliminating the need for arbitrary "Sprints".
