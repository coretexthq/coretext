## Summary
Established the architecture for Coretext v2 using Deterministic State-Driven Development (D-SDD). Shifted away from probabilistic vector search and heavy managerial frameworks (like BMad) to a minimalist, SQLite-driven routing engine (`experience.json`). Implemented a Symmetrical Adversarial Contract between isolated subagents (Planner, Executor, Reviewer) connected by a strict Triad of Execution: Semantic Goal (`target_state.md`), Technical Gate (Failing Tests), and Ephemeral Scope (`atomic_step.md`).

## Highlights
- **The "Testing Squeeze" (The Planner Bottleneck):** Current LLMs are notoriously bad at writing tests for code that doesn't exist yet. If the Planner writes a bad test, the Executor will write bad code to pass it. Rigorously monitor the quality of the Planner's test output.
- **The Frontend UI/UX Blindspot:** TDD is exceptionally difficult for visual UI changes. You will need to explicitly define how visual UI changes are verified (e.g., relying entirely on the Reviewer's semantic audit for CSS changes, bypassing the strict test gate).
- **JSON Corruption by the Reviewer:** LLMs are prone to corrupting JSON syntax. You must build a mechanical schema validator that runs before the Reviewer is allowed to commit its changes to `experience.json` to prevent crashes in the SQLite injection engine.
- **Human Context Fatigue:** You are the final "Semantic Diff Tool." When the project scales, your biological "Mental Model" will degrade. Building a Visualization Graph UI for `experience.json` is a critical survival tool to avoid becoming the bottleneck in your own headless software factory.
- **The Ultimate Determinism (Linters & AST):** The endgame of D-SDD is to constantly push knowledge down the funnel: from Discovery (`knowledge/*.md`) -> Formalization (`ARCHITECTURE.md`) -> Mechanization (Custom Linter Rules/AST Enforcement). Linters act as a zero-token "electric fence" that instantly blocks non-deterministic LLM errors.

## Problems & Solutions
- **Problem**: Enforcing constraints using generic natural language policies or prompt "slop" is unreliable and leads to agent hallucination or "green-washing" (passing tests without intent alignment).
  - **Solution**: Shift the contract from Instructional to Adversarial & Mechanical. The Planner writes a failing test (Technical Contract), the Executor strictly satisfies it, and the Reviewer performs a Semantic Audit against the global `ARCHITECTURE.md`.
- **Problem**: "Topological Blindness" in probabilistic vector search causes agents to systematically miss cross-cutting global architectural constraints.
  - **Solution**: Replace the vector graph with a deterministic SQLite routing ledger (`experience.json`). Define strict edge enum types (`docs`, `knowledge`, `templates`) to mandate exactly how context is injected (e.g., forcefully injecting `ARCHITECTURE.md` to the Planner, passively hinting `knowledge/*.md` to the Executor).
- **Problem**: Storing historical intent and lessons in a monolithic `changelog.md` corrupts line-number-based SQLite indexing as the file grows.
  - **Solution**: Decouple the knowledge base into atomic, immutable files (`knowledge/*.md`). The file path becomes the permanent primary key for the SQLite graph. Delegated temporal tracking entirely to Git.
- **Problem**: The Reviewer agent only sees the Planner's interpretation of the human intent (`target_state.md`), risking "Silent Architectural Rot" if the Planner misinterprets the human.
  - **Solution**: Acknowledge the "Lossy Human" limitation but position the human as the final "Semantic Diff Tool" who approves the Reviewer's `handoff.md` against their own mental model, avoiding prompt noise while preventing agent collusion.
- **Problem**: Even with a rigid Planner/Executor/Reviewer loop, LLMs are fundamentally non-deterministic and can output bad syntax, hacky workarounds, or hallucinate dependencies to pass tests.
  - **Solution**: Move constraints from the LLM's prompt into the physical environment. Implement AST Enforcement (code must parse cleanly before being written), Sandboxed Execution (Nix/Docker restricted environments), Property-Based Testing (to defeat lazy implementations), and compile `knowledge/*.md` lessons into Custom Linter Rules (Restrictive Enforcement) that act as an "electric fence" blocking bad code in CI with zero token cost.
- **Problem**: The Planner might get its context contaminated if it reads messy human draft notes and brainstorms.
  - **Solution**: Strictly isolate human ideation. Migrate `backlog.md` to GitHub Issues or a separate directory not ingested by the agent. Hand the Planner only sanitized, final "Issue Descriptions".
